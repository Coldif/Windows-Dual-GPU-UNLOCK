# MSI B550M / RTX 3090 headless USB evidence (local profile, no iGPU, no EDID driver)

## Provenance and build scope

Contributor-reported results from one machine on 2026-10-26, made with a local profile generated by
`research/profile/make-profile.py` from two read-only probe captures of that machine. They are not a
reviewed machine profile and not a maintainer-operated hardware test. The EFI hashes in
[summary.json](summary.json) depend on that machine's `profile-local.h` and are not expected hashes
for any other machine.

## Machine

MSI B550M PRO-VDH WIFI (MS-7C95, BIOS 2.O1, AMI), Ryzen 7 5700X (no iGPU), MSI RTX 3090 24 GiB
(GA102, `10de:2204` / `1462:3881`, VBIOS 94.02.42.00.2f) at `0000:2b:00.0`, two monitors on the RTX
and no other display adapter. Three things differ from every reviewed profile and are what this
evidence covers:

| | Reviewed profiles | This machine |
|---|---|---|
| RTX PCI bus | `01` | `0x2b` (`GU_TARGET_BUS`; the child log prints `0:43:0.0`, decimal) |
| Integrated GPU | present (or aggregate console) | none; the RTX owns the only GOP |
| AMI EDID/mouse driver on the RTX GOP | bound, stopped in stage 3 | none bound (`GU_NO_EDID_DRIVER`); stage 3 skipped |
| nvgop | `0x60008` / `0x60010` | `0x60009`, `.text` `d045cee2...` |

The PciIo attribute cache was `0x300` with PCI command `0x0003` in both probe captures and at release
time (`BME containment: ... cached=0x300`).

## Recorded hardware runs

Route: headless wrapper/child from a FAT32 USB stick (`GU_USB_MEDIA`), chosen in the firmware boot menu.

| Run | Boot | Entry SS0 / SS1 | Result |
|---|---|---|---|
| AUTO000000 | cold boot after a full shutdown | `0x1320155` / `0x6` | `FINAL status=0 clean=1`, one FLR, Windows started directly, both monitors on the RTX working |
| AUTO000001 | Windows restart | `0x1320155` / `0x6` | same |
| AUTO000002 | Windows restart | `0x1320155` / `0x6` | same |

Every run ended with `SS0=0x88888888 SS1=0x8`, WPR2 cleared after FLR, BME off and no retained
mappings. A Windows restart resets the GPU on this board (the pre-check found it cold each time), so
the unlock does not survive a restart. The wrapper log records `no-edid-driver-on-this-firmware`,
then the NVIDIA GOP detach, decode restore, `verify-complete` and Windows `StartImage`, all status 0.
See [report-excerpt.txt](report-excerpt.txt).

## Measurements

PyTorch 2.13.0+cu130 `torch.matmul`, FP16/BF16 with FP32 accumulation, FP32 with TF32 off; median of
5 runs of 20 matmuls, TFLOPS. Same driver (617.14), power limit (350 W) and script in both states.

| n | Mode | Locked | After AUTO000000 | After AUTO000002 |
|---|---|---|---|---|
| 4096 | FP32 (control) | 23.0 | 23.4 | 23.6 |
| 4096 | TF32 | 32.2 | 56.9 | 56.0 |
| 4096 | FP16 | 64.3 | 110.9 | 115.2 |
| 4096 | BF16 | 66.2 | 115.9 | 115.6 |
| 8192 | FP32 (control) | 24.6 | 25.3 | |
| 8192 | FP16 | 67.5 | 93.3 | |
| 8192 | BF16 | 68.3 | 89.9 | |

At n=8192 the unlocked card sits at its 350 W power limit (power cap active in 15 of 21 telemetry
samples, average SM clock 1507 MHz), so the gain there is smaller. The repository's cuBLAS benchmark
was not run on this machine.

## Not established

The pre-check skip branch and the BootOrder fallback on hardware; sleep and hibernate resume;
long-term stability and application performance; the internal-ESP route; any other board without an
EDID driver. Excluded: PROM image, raw probe and handle-graph logs, driver dumps, partition and disk
identifiers.
