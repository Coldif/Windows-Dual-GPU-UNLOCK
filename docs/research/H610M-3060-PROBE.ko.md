# Gigabyte H610M H / RTX 3060 12GB 읽기 전용 프로브

이 문서는 이 PC의 프로필 후보 값을 **언락 없이** 수집하는 observation 프로필을 설명한다.
원 기여 `4b748f5`의 수집·실기기 기록과 이후 통합 보완을 구분한다. 별도의 쓰기 프로필
`h610m-3060`은 [호환성 문서](../COMPATIBILITY.ko.md)의 정확한 USB 구성에만 해당한다.

## 대상 구성

| 항목 | Windows에서 확인한 값 |
|---|---|
| 보드 / BIOS | Gigabyte H610M H / FC (AMI) |
| CPU / iGPU | Core i5-14400 / UHD 730 `8086:4682` 활성 |
| GPU | Gigabyte RTX 3060 12GB, `10de:2504`, subsystem `1458:4096` |
| 화면 | 모니터 2대 모두 RTX에 연결(headless 경로 후보). iGPU 경로는 선택 사항 |
| 드라이버 | NVIDIA 610.88 |

## 바뀐 코드

- `machine-profile.h`: `GU_PROFILE_PROBE_H610M_3060`. PCI ID와 subsystem만 정의한다.
  BAR, VRAM, PROM, 화면 경로, 드라이버 지문은 정의하지 않으므로 쓰기 쪽 코드는
  컴파일되지 않는다. `GU_DIAGNOSTIC_ONLY`(또는 호스트 테스트용 `GU_PROBE_HOST_TEST`)와
  `GU_DIAGNOSTIC_PROBE`가 없거나 release/unlock define과 함께 쓰이면 `#error`로 멈춘다.
- `build-diagnostic.ps1`: `-HardwareProfile`, `-UsbMedia`. 기본값은 기존과 같은 빌드다.
- `handoff.c`: 진단 전용 USB 빌드는 실패하면 멈추지 않고 펌웨어 부팅 순서로 돌아간다.
  이 이미지는 드라이버 해제나 GPU 쓰기를 하지 않기 때문이다.
- `research/headless/build-observe-usb.ps1`, `stage-observe-usb.ps1`: USB용 관찰 EFI를
  빌드하고 USB에 복사한다. 부팅 항목, BootOrder, 펌웨어 설정은 바꾸지 않는다.
- `test-diagnostic.ps1`: 프로브 전용 프로필의 모의 테스트와, 쓰기 쪽 define과 함께
  컴파일하면 실패하는지 확인하는 음성 테스트를 추가했다.

## 실행 전 확인

1. 모니터는 제보 당시처럼 RTX에 둔다. 이 observation은 해당 headless 구성의 자료를 수집한다.
   BIOS: `Initial Display Output = PCIe 1 Slot`, CSM 끔, **Secure Boot 끔**.
   iGPU 경로도 비교하려면 모니터 1대를 메인보드 단자로 옮겨 추가 캡처를 1회 한다.
   EFI는 화면 구성과 상관없이 같은 파일이다.
2. BitLocker가 켜져 있으면 복구 키를 먼저 백업한다. Secure Boot를 바꾸면 복구 키를 물을 수 있다.
3. FAT32 USB를 준비한다. 스테이징은 `EFI\BOOT\BOOTX64.EFI`와 빈 `RTX3090-UNLOCK\` 폴더만 만든다.

## 빌드와 스테이징

```powershell
.\research\headless\build-observe-usb.ps1 -WindowsEspGuid 'WINDOWS-ESP-GUID' `
  -Clang C:\TOOLS\LLVM20\bin\clang.exe -LldLink C:\TOOLS\LLVM20\bin\lld-link.exe
.\research\headless\stage-observe-usb.ps1 -Drive D
```

## 실행 (3회)

1. Windows를 **완전히 종료**한다. 빠른 시작을 켜 두었다면 `shutdown /s /t 0`을 쓴다.
2. 전원을 켜고 F12 부팅 메뉴에서 USB(UEFI)를 고른다. 키를 더 누르지 않는다.
3. "GPU console diagnostic only..." 문구가 나온 뒤 Windows가 정상 부팅되면 끝이다.
   실패하면 "Nothing was changed"를 출력하고 다음 부팅 항목으로 넘어간다.
4. Windows에서 USB의 `RTX3090-UNLOCK\` 안 DIAG/IMG/PROM 전체를 회차별 별도 로컬
   `research/results/`(Git 무시)에 보존한다. 복사한 자료가 온전한지 확인한 뒤 원본 세트도
   별도 archive로 옮겨 활성 폴더를 비운다. **기존 덤프를 덮어쓰지 않으며**, 파일이 남아
   있거나 존재 여부를 읽지 못하면 새 capture가 불완전으로 표시된다. 재스테이징도 거부한다.

통합본은 BAR/MEM/BME와 할당 후 PCI snapshot을 확인한 뒤 GPU 데이터를 RAM에 수집하고
그 후 로그를 기록한다. USB·코드·설정·실행물 해시와 capability 타입도 복사 전에 확인한다.
EFI 파일 API의 부재 확인 후 CREATE는 원자적 독점 생성이 아니므로 같은 USB에 다른
writer를 실행하지 않는다. 실패·누락 MMIO는 후보 보고서에서 null이며 실제 0과 구분된다.
동일 폴더의 세트만 함께 분석하고, 기존 결과를 새 통합본의 실기기 검증으로 확대하지 않는다.

세 번의 콜드 부팅에서 같은 값이 나오면 프로필 후보로 쓴다.

## 공개하지 않는 것

`IMGnn.BIN`(펌웨어 드라이버 이미지), PROM 내용, 원시 DIAG 로그 전체, 파티션 GUID.
보고서에는 정리한 값과 해시만 넣는다.

## 결과 (2026-10-26)

### 프로브

콜드 부팅 3회와 PROM 저장 1회, 모두 `probe status=0`이고 Windows로 정상 인계됐다. SS0/SS1 진입값을 뺀 값이 모두 같았다.

| 항목 | 값 |
|---|---|
| BDF / 루트 포트 | `0000:01:00.0` / `00:01.0` |
| BAR0 | `0x42000000`–`0x42ffffff` (Windows 자원 할당과 일치) |
| 칩 / VRAM | `0xb76000a1` (GA106) / `0x3000` MiB |
| PROM SHA-256 | `727dd833…a808c9` (덤프 파일과 일치) |
| 콜드 상태 | PLM `0xffffff8f`, GFW `0x8b8f/0x3ff/0x10`, WPR2_HI 0 |
| SS0 / SS1 진입값 | `0x06204001`/`6`, `0x06206001`/`4` (부팅마다 다름) |
| 화면 | RTX 물리 GOP 1개, Intel GOP 없음. nvgop 화면 자식 2개(모니터 2대) |
| nvgop | `0x60010`, .text SHA `615b37a7…` (B660M, X870과 같음) |
| FWSEC-FRTS | PROM `0x416bc`, `0xea00`바이트, 서명 3개 (versions `0x7`) |

지문은 `research/headless/fingerprint_probe.py`로 뽑았다.

### 호스트 테스트 (`GU_PROFILE_H610M_3060`)

- `test-diagnostic.ps1`: 통과.
- `test-cold-precheck.ps1 -HardwareProfile h610m-3060`: 콜드 사전 점검 180개와 인계 흐름 39개 통과.
- `test_efi_transaction.c`: 실제 PROM, 검증된 에셋 5개, 프로브 설정 공간으로 112개 시나리오 통과.
  `-DGU_INTERNAL_BOOT -DGU_EXPERIMENTAL_3090 -DGU_ENTRY_LATCHED_SS1_FULL` 조합이고,
  FRTS는 `0x2ffe00000`에 패치된다.
- `build-usb.ps1 -HardwareProfile h610m-3060`: 빌드와 PE 검증 통과. 바이너리에는 3060 값만 있다.
- 실행하지 못한 것: 앱 단계 모의 테스트(`test_3090_preflight.c`, `test_entry_latched.c`,
  `test_3090_experimental.c`). 이 테스트들은 3090 칩 ID와 AMD 화면 mock이 하드코딩돼 있다.
  `test-all.ps1`의 기본 작업은 원작자 PC의 3090 캡처를 요구한다.

모의 테스트 통과는 소프트웨어 증거일 뿐 하드웨어 지원 증거가 아니다.

### 하드웨어 언락 1회 (2026-10-26, USB headless, `GU_PROFILE_H610M_3060`)

래퍼 `74c4d19a…`, 자식 `82998f48…`. F12로 USB를 골라 부팅했다.

- `HLS000000`: 그 부팅에서 RTX GOP가 0개였다(모니터 미인식으로 추정). `console-prepare-preflight`가
  `EFI_NOT_FOUND`로 거부했고, 아무것도 해제하지 않은 채 펌웨어 부팅 순서로 돌아갔다.
- `HLS000001` / `AUTO000000`: 성공.

리셋 없이 Windows로 진입했고, NVIDIA 610.88이 화면 2대를 복구했다.

| 8192³ GEMM, FP32 누적, 170 W, 5회 중앙값 | 잠금 상태 | 언락 후 | 변화 |
|---|---:|---:|---:|
| FP16 | 27.06 | 46.61 TFLOPS | +72% |
| BF16 | 27.18 | 46.28 TFLOPS | +70% |
| TF32 | 13.50 | 24.02 TFLOPS | +78% |
| FP32 | 9.58 | 9.34 TFLOPS | −2.5% (클럭 하락) |

언락 후에는 전력 제한에 걸려 SM 클럭이 1950에서 약 1785 MHz로 내려간다. 같은 스크립트
(`gpu-unlock/windows/bench_gemm.py`, torch 2.10.0+cu126)로 측정했다.

아직 확인하지 않은 것: 반복 콜드 부팅 안정성, Windows 재시작 후 상태, 절전(S3) 복귀,
실제 애플리케이션 성능, 장시간 안정성.
